# 历史方案：动态对象装配路线已取消

2026-10-13 用户选择继续离线编译输入视图。本文后续内容保留历史讨论与探针证据，不再作为实施顺序。当前分别执行[离线导出提速](offline-export-performance-plan.md)和[游戏更新自动适配](game-update-prefab-adaptation-plan.md)。

# Prefab 加载后适配与缓存改造计划

状态：阶段 1 部分实机证明、阶段 2/4 部分核心代码已完成，生产链尚未切换。当前接续点为 Typhoea NPC 入口验证，具体执行顺序见[本轮实施清单](#11-本轮实施清单2026-10-13)。本文不表示新方案已经完整接通或比现方案更快。用户授权修改三端、数据结构及现有 Mod，不保留旧包读取兼容分支；部署切换前统一迁移现有 Mod。

## 1. 目标与确定的职责

替换链改为：作者端准备原生资源 → 游戏正常加载来源 Prefab → 在首次消费者初始化/实例化前匹配 Mesh → 建立候选模板 → 游戏沿自己的入口创建实例。

主要解决的问题是：旧导出固定了当时的 PFB 消费者集合，游戏更新后新增或变化的消费者可能没有对应规则。新链路在游戏已经读取并解析 PFB、但尚未实例化和初始化消费者时，依据当前实际 Mesh 引用适配。把工作移到这个边界能解除旧消费者清单的约束，但不会自动消除装配成本；首次发现和冷原生加载必须单独测量。

- 游戏新增剧情、NPC、UI 或特效 Prefab，只要仍引用目标 Mesh，就在实际加载/创建时适配，无需重新导出 Mod。目标 Mesh 被删除、改名或结构实质变化不承诺自动修复。
- INI 仍是唯一规则入口。Mesh 的逻辑路径与资产身份决定命中；材质、贴图和 Shader 来源只决定依赖，不扩大替换目标。
- 每个命中的原 Renderer 应用完整 0/1/N 作者 Part；未声明资源保持原样。不能把多部件展开简化成一次 sharedMesh 设置。
- Blender 编译作者资源及与消费者无关的装配声明，不枚举、修改或验证所有游戏 PFB，不保存完整原游戏依赖。
- DLL 按游戏加载事件绑定资源、适配候选及管理实例；不生成几何、不转换图片、不启动编译器，不在帧循环里发现 PFB、解析来源或校验缓存。
- 正常加载与 F10 使用同一规则和候选构建入口。F10 提交当前 mods 的完整集合，增删改和空集合走同一流程。
- DLL、Blender、AnimeStudio 安装文件保持隔离。普通玩家不需要 Blender、解包索引或作者编译器。

这是对现行“离线绑定全部消费者、DLL 回放来源字节”路线的替代，不能在生产端长期保留两套替换后端。现行可工作的代码在验证和切换之前保留；旧路线只用于开发对照，不成为新版的自动回退分支。

## 2. 必须先证明的三件事

### 精确来源绑定

INI 的 path + asset 要能对应当前进程中的准确 Mesh 对象。优先使用游戏资源目录和加载请求提供的逻辑身份，结合来源 Bundle/成员身份及有效对象寿命。旧 CAB/PathID 只能用于同内容资源的定位缓存，不能作为游戏更新后的永久锚点。

Prefab 中已经解析好的 sharedMesh/过滤器引用用于判断对象是否匹配。同名 Mesh、同名 Renderer 或相同顶点数都不能代替准确来源。异步结果、以 hash 取资产、依赖隐式加载、同名不同来源及非公开可读 Mesh 都必须覆盖。

如果正常加载信息不能完成准确绑定，先验证能否只读当前相关资产目录/容器元数据完成绑定；必须计量这一步，不允许静默退回全游戏解包、场景扫描或主动加载未访问的角色。

### 初始化时机

要证明能取得原 Prefab，并在游戏缓存 Renderer、骨骼或物理状态之前完成候选修改。验证同步、异步、提前预加载和对象池创建入口。

候选不能原地修改游戏原 Prefab、源 Mesh 或源 Material。候选模板构建自身也不能提前触发 Awake/OnEnable、物理工作、动画事件或其他脚本副作用；不能假定普通 Instantiate 后再禁用就满足条件。记录实际回调顺序，确认游戏消费者看到的是完整候选。

### 作者资源独立加载

当前 .mesh/.mat/.tex 是增量交换载荷，不是能直接交给 Unity 的独立资产包。新导出必须产生合法的作者资源装载结果，保留游戏需要的 Mesh 原生字段，同时独立处理作者 Texture 和来源材质/Shader 的绑定。

使用一个真实蒙皮 Mesh 和一个来自其他角色的材质完成最小实机证明。确认首次加载不依赖旧 compiled.bin 的固定 PFB、旧 CAB 对象编号或旧工作区索引；不能以 public Mesh setter 可画出来代替完整 metadata 验证。

这三个验证是后续切换的前提。任一无法证明，就记录具体缺口并调整入口或资源布局，不把不完整后端推广到全部 Mod。

## 3. 新数据结构

### 分发内容

分发内容分为 INI、作者原生资产和紧凑装配描述。作者资产保存完整几何、权重、bindpose、形态数据、纹理 mip 及必要原生模板；装配描述保存目标逻辑身份、Part 与资产映射、骨骼相对路径、新增节点/组件及材质属性绑定。

物理文件组织先在最小独立加载证明中确定，然后只保留一种生产布局：大几何和像素只保存一次，禁止在交换文件和编译容器中重复分发。按独立资源组织可复用块，使材质参数修改不要求遍历消费者或重新编码未变贴图。

材质保留独立作者变体。当前游戏来源材质/Shader 按逻辑身份绑定，未覆盖的来源属性继承；改过的属性、keyword、queue 和贴图引用按作者声明应用一次。同一原材质的多个作者变体不得互相覆盖。借用来源的依赖只按实际需要加载，并使用正确的异步请求/完成和租约；禁止在加载钩子内重入阻塞同一个资源队列。

运行描述不保存全部 PFB、Renderer 地址、游戏物理文件范围或所有消费者骨骼描述。旧 source-inputs.bin 和固定消费者 compiled.bin 的生产读取路径最终移除。允许重新定义现有文件名，但以新实际结构判断兼容，不按游戏/插件版本号分支。

### 玩家缓存

持久缓存放在 plugin 内的派生缓存目录，不写回作者 Mod，不依赖作者机器绝对路径。它保存命中与未命中结果、来源引用、层级/骨骼路径及需要补齐的装配位置，不保存运行中 Unity 指针、InstanceID、物理 Job、动画状态或完整原游戏包。

基本身份包含：当前来源 Prefab 身份、影响匹配/装配的依赖内容身份、作者资源/规则摘要、缓存自身的数据结构。控制数值及按键开关不触发资产适配失效。

- 优先采用游戏资源条目提供的可靠内容摘要。文件时间/大小仅为快速筛选，不作为内容正确性的唯一证明。
- 只在启动绑定资源目录、目录挂载变化、实际加载请求及 F10 规则变化时核对；可靠内容身份不变就不重复解析。无法取得可靠摘要时，相关范围的内容核验成本必须实测。
- 未见过的 PFB 没有缓存，在自己的第一次加载/创建事件中检查。缓存未命中不等于永远忽略；资源、依赖或 Mod 规则改变后重新判断。
- 新进程仍要加载作者资产、绑定当前对象并建立候选模板。磁盘缓存节省发现/计算，不等于跨进程保存 Unity 模型。
- 来源模板卸载或指针复用按寿命事件退休内存记录。不定期扫描所有 Renderer，也不设置资源/缓存条目数量硬上限。

一个 PFB 第一次检查时记录实际 Mesh 引用，建立 Mesh → 已观察 PFB 的反向关系。未命中的已加载 PFB 也要能在新增 Mod 后被重新判定；已有资源实例与模板使用不同记录。内存索引只持有必要弱身份或明确租约，不能为索引永久钉住所有原游戏资产。

## 4. 运行路径

### 启动与正常加载

1. 读取当前完整 Mod 集合，建立目标 Mesh 与作者资产索引。只解析启动必需的小型目录，不提前整理所有消费者、展开所有作者载荷或预加载所有角色。
2. 游戏自己的同步/异步请求获得来源 Prefab。记录准确资产身份与寿命；非 Prefab 或没有有效 Mod 的请求直接走原流程。
3. 查询内存结果；没有可用结果时核对磁盘适配缓存，再决定是否检查这棵 Prefab 的实际 Mesh 引用。包括 inactive 子节点，范围始终是这份资源，不是全场景。
4. 没有匹配就记录未命中并返回原资源。匹配时只加载实际需要的作者资产及材质依赖，按同一装配入口生成候选。
5. 完成引用、骨骼、组件和控制登记前置条件验证，再让游戏从候选创建实例。异步请求只完成一次，不能阻塞等待自身加载队列，也不能在异步线程调用 Unity 对象接口。
6. 普通已准备的实例化仅查询有效候选，不重新遍历 Renderer 或解析磁盘缓存。候选变更仍通过资源/代际事件失效，运行中模板被游戏修改的情况需要明确事件覆盖。

加载完成监听与实例化监听分别承担提前准备和入口兜住的职责。仅有某个角色的 LoadModel 回调不满足全部资源覆盖；以 hash 取资产、异步结果 getter、PrefabInstantiateProxy、普通/异步 Instantiate 和池创建都需要对照真实调用链确认。

### 装配必须保持的内容

| 内容 | 新路径要求 |
| --- | --- |
| Mesh 原生数据 | 顶点/索引布局、法线/切线/UV、权重、bindpose、骨骼身份、形态通道、可读性和 bounds 完整，不依赖 GPU 私有内存复制 |
| 蒙皮绑定 | 用当前具体 Prefab 骨架作用域解析路径，骨骼顺序与作者 bindpose 一致；同名骨骼不能跨作用域绑定 |
| 0/1/N Part | 每个命中的原 Renderer 得到完整作者部件集合，其他 Renderer 保留；静态网格不伪造骨架 |
| LOD 与 Helper | 更新游戏实际缓存的 Renderer 列表、分类及 enabled 初始语义，不能只添加子 GameObject |
| 材质与依赖 | 独立变体、Shader、全部继承贴图、keyword/queue、来源租约及作者资源引用有效 |
| 骨骼与物理 | 按当前骨架新增节点/组件、重绑定 Selection 与碰撞引用，同骨架去重；游戏构建/动画写回/蒙皮槽分开处理 |
| 控制 | 世界、UI、NPC、inactive 部件都完成登记；Ins 保持每 Mod 独立启用与持久化，同键多 Mod 可共存 |
| 生命周期 | 保留动画、武器、音频、跟随物、临时动作预加载与实际原生退出契约 |

### F10

F10 读取当前完整 mods 集合，只为实际受影响且已观察到的 Prefab/owner 建立下一代候选；未来资源加载查询最新规则。新增 Mesh 目标也通过已观察 PFB 的反向关系命中，不要求场景扫描。

无资源变化的 F10 只更新设置和控制；资源增删改按资源摘要复用未变资产，受影响候选准备完成后统一发布。沿已适配的游戏 owner 流程迁移世界、UI、NPC，保留失败回滚。删除 Mod 的来源模板自然成为候选，空集合走相同流程。

只改未来模板不会刷新当前人物或已创建的对象池实例。已存在的池对象、特效和捕获结果必须记录其真实 owner/寿命；只在安全池边界重建或失效，不能破坏活跃动作或物理工作。没有证明的 owner 不得被报告为已经刷新成功。

候选发布、活跃实例迁移和旧资源退出分开计量。原资源和前代作者资产保持到实际消费者/Job/捕获生命周期退出；普通 Bundle 卸载不等于这些消费者已经结束。

## 5. 实施顺序与交付物

| 阶段 | 工作 | 推进到下一阶段的条件 |
| --- | --- | --- |
| 1：最小入口证明 | 准确 Mesh 绑定、同步/异步与预加载入口；一份独立作者 Mesh、一份跨角色材质、无初始化副作用的候选 | 不依赖旧 PFB 清单，作者 Mesh metadata 正确，原资源未改，实际加载与回调顺序有证据 |
| 2：新作者格式 | 独立原生资产及紧凑装配描述；Blender 全部/分资源导出；AnimeStudio 只补必要身份和模板 | 导出不枚举 PFB；同内容复用和材质参数导出不重编码未变贴图；无大载荷重复分发 |
| 3：通用匹配与装配 | 准确资源索引、未知 PFB 首次匹配、0/1/N、LOD、Helper、骨骼与新增物理 | 主角/UI/NPC 同一规则入口；新 PFB、同名不同 Mesh、多骨架及外部材质案例通过 |
| 4：持久缓存 | 命中/未命中缓存、来源/依赖变化、规则增删、指针复用与退休 | 新 PFB 首次事件被识别；依赖单独改变也失效；缓存热路径不重复扫描/解压/哈希，不进入帧循环 |
| 5：F10 与特效池 | 完整集合提交、已有 owner 迁移、对象池、预加载特效、残影/烘焙资源及生命周期 | 启动/F10 使用同一构建入口；修改、删除、新增、空集合及多次重载不丢模型、不 T pose、不持续掉帧 |
| 6：迁移与切换 | 统一修复现有 Mod、清除生产旧后端、三端本地部署及文档更新 | 现有使用功能有实机确认，性能达标；生产包仅一条替换路线，没有旧包兼容、作者编译器或 AnimeStudio 运行依赖 |

每个阶段包含对应的最小回归与真实边界对照，不另建通用脚本执行平台、常驻外部服务或完整游戏资源副本。引入模块按资源装载、准确身份、Prefab 装配、缓存与寿命分工；不要围绕具体角色建立分支。阶段 4 的内存缓存、事件失效及计时在阶段 3 的第一个运行链中接入，不能等完整装配结束后再补性能；磁盘缓存随后接入。

## 6. 特效覆盖验收

至少分别确认以下路径，不以常态看不到特效作为未加载的证据：

- Prefab 已预加载但未实例化：在资源事件准备候选。
- 首次触发才加载：在实际请求/完成中准备，回调不重复、不死锁。
- 对象池已创建但尚未显示：创建前适配，F10 对存量池对象按其真实退出边界处理。
- 特效 Prefab 直接引用目标 Mesh：应用同一准确匹配。不同 Renderer 类型的 Mesh 引用必须逐类确认；只检查 SkinnedMeshRenderer/MeshFilter 不等于完整特效支持。
- 动态复制/烘焙/抓取 Mesh 的残影：保留并核对现有捕获适配，不能假定 PFB 静态引用覆盖这种生成路径。
- 原场景资源中已经存在的对象：确认其创建是否经过观测入口。不能把没有再次 Instantiate 的对象当作已覆盖，更不能用全场景周期扫描补洞。

## 7. 性能验收

性能第一。相邻对照用同一份 Mod、同一游戏操作和相同缓存条件；记录插件增量耗时、游戏自身加载耗时、主线程最大单次工作、帧时间分位数、内存及 GPU 资源存量。不能只测提交函数、只把工作移到 F10 前或把游戏等待算成插件优化收益。

| 场景 | 必须达到/证明的结果 |
| --- | --- |
| 没有 Mod 的请求 | 快速原路径，不能新增 Prefab 遍历或磁盘缓存工作 |
| 缓存热路径 | 插件匹配/选择候选目标低于 1 ms，且不随已知 PFB 总数线性遍历；这是验收目标，不是已有测量 |
| 首次未知 PFB | 单独记录检查、作者加载、装配、依赖等待和主线程工作；不重复解压原 PFB，不出现同步队列死锁 |
| 首次启动 | 不再有全消费者准备；按当前实际需要加载，插件自身成本与游戏就绪等待分开 |
| 材质参数导出 | 工作量与变化的材质有关，未变几何/像素不重新处理；不因消费者有几十或上百 PFB 增长 |
| 完整导出 | 与当前 Allure 24.07 秒完整入口比较；当前 3.50/20.32/0.26 秒分别是作者/编译/发布，不能把编译阶段全部当作可删除 |
| F10 | 已准备且无资源变化的提交目标为毫秒级；资源变化时分别报告候选准备与实际实例迁移，不能隐藏后续异步工作宣称完成 |
| 多代/多 Mod | 连续 F10、反复 UI/世界/NPC 切换后帧率恢复、旧资产和池对象按寿命释放；使用合成独立 Mod 与真实集合分别确认扩展性，不设人为容量上限 |

若动态首次装配造成更大的主线程尖峰，不能仅凭导出更快或启动日志更短切换。优先削减重复对象创建、按资源共享作者资产、提前利用真实预加载事件；Unity 操作不能扔到普通工作线程伪造异步。分帧推进仅用于已发生的待完成操作，不成为每帧资源扫描。

性能记录必须区分以下四种状态，不使用一个“缓存开启”标签混合报告：

| 状态 | 允许的必要工作 | 必须排除的重复工作 |
| --- | --- | --- |
| 新进程、无适配缓存 | 当前未知 PFB 一次发现、按需作者资产加载、候选构建 | 扫描全部游戏资源或全部 Mod 载荷 |
| 新进程、有有效磁盘缓存 | 绑定本进程来源/骨骼、加载作者资产、建立本进程候选 | 重新发现整棵 PFB、持久化/恢复 Unity 指针 |

同进程已就绪路径以插件增量 p99 < 1 ms 为初始门槛，游戏自身 Instantiate 时间另记。首次发现、未命中和冷装配记录 p50/p95/p99、最大值、主线程最大连续占用、受影响帧时间及资产数量。待处理 Unity 工作先以 4 ms/帧作为可调整软调度预算；单次不可分割的原生加载/克隆调用若超出，必须记录并调整预加载或资产组织，不能声称分帧已经解决。最终切换要求同一场景的帧时间 p95/p99 和加载交互没有相对现行链路的可重复退化；这些都是待实测门槛，不是已有结果。

无有效 Mod 时不发现 PFB。有有效 Mod 但首次遇到无关 PFB 时，除非已有可靠依赖信息能证明不命中，仍可能需要一次发现；这项成本也必须报告，不能将所有“未命中”都描述为零开销。重复未命中直接复用有效结果。

### 三级身份与缓存内容

1. **Bundle/成员目录。** 当前资源挂载域、Bundle 内容身份和 SerializedFile/CAB 成员身份，记录容器内各资产入口的准确映射及依赖。目录可以按容器复用，不能用 Bundle 路径或游戏 `hashName` 未经证明地替代内容身份。
2. **具体 PFB 观察与装配计划。** 按资源域内的具体资产身份区分 PFB，逻辑路径为定位别名；同一内容代际内的成员身份和根对象标识共同定位。有效性包含来源/结构与相关依赖内容身份。磁盘保存所有 Renderer 的组件地址/类型、准确 Mesh 身份、骨骼作用域与路径、LOD/helper 等装配关系，规则变化再匹配这些观察，不一定重扫整棵层级。规则结果与候选装配计划另绑定完整规则/作者摘要。
3. **本进程就绪资产与候选。** 内存共享按内容确定的作者 Mesh/Texture/私有材质；每个具体来源 PFB 和规则代际拥有自己的候选模板、骨骼绑定及控制登记。绑定当前原生对象和寿命，不能把 Unity 指针或 InstanceID 写入磁盘。就绪查询不重扫层级、不读文件、不重新加载资产。

磁盘缓存不是仅保存一个路径，也不保存原游戏 Bundle/PFB 完整副本。新进程仍需要装载原生作者资产并构建本进程候选；持久缓存节省发现、匹配及装配位置计算，不等于缓存了一个可直接恢复的 Unity 对象。源码的 `eiem_prefab_match_cache.h` 当前只有 path/content/dependencies 和消费者观察核心，尚未挂接生产资源事件；资源域/具体根身份、完整骨骼和列表计划仍须补齐，不能将该核心描述成已经实现的三级缓存。

### 多个 PFB 位于同一 Bundle

必须允许 `Bundle A / CAB-1 / 根 101`、`Bundle A / CAB-1 / 根 202` 和 `Bundle A / CAB-2 / 根 101` 三条独立资产记录。Bundle 目录与内容核验共享一次，三个 PFB 分别发现、匹配、构建与发布；它们可共享相同作者 Mesh/Texture，骨架和候选不能共用。任何一个 PFB 未命中不代表整包未命中；包已经加载也不代表其中所有 PFB 已加载或验证。处理实际请求的资产，不为补覆盖而主动实例化整包全部 PFB。

更新后首先核验当前目录及内容：旧 CAB/根对象标识仅在对应内容仍有效时可复用；变更后重新定位并失效相关记录。只有 Bundle 粗粒度摘要可用时，可以保守失效其下 PFB，不能伪称已实现逐资产精确失效。PFB 地址与骨骼路径要在当前资源中绑定验证，不能因为逻辑路径没改就接受旧计划。

新回归须加入同包多 PFB、跨 CAB 相同 PathID、相同逻辑路径的不同资源域、包内某根单独改动、共享 Mesh、多 Renderer/全 LOD 以及局部未命中不抑制其他根。当前真实 Typhoea 样本的 22 个消费者分布在 22 个 PFB 输入中，尚不能代替共包场景的验证。
