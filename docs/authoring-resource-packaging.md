## 解包格式的当前判断

后续核对用户现有 `E:\EIEM_Workspace\assets\beyond\dynamicassets\gameplay\actors\postmodels\characters\chr_0032_lizhiyan_postmodel.eiem`：它是作者目录，包含 66 份 EIEMESH v6、27 份材质、50 份 PNG、1 份骨架、mod.ini，以及 physics 下 66 份组件原字节和对应 JSON/schema。它不是完整可原样写回的 SerializedFile/AssetBundle。

当前无需推翻解包侧已有 Mesh/Material/Texture/Skeleton 编辑格式。解包侧的最小改动是增加版本化来源/装配清单，并改进提取行为：准确的容器入口与资源身份、每次 Renderer 使用的 Mesh/Material/骨骼/LOD 上下文、当前源对象/schema/流数据的定位。原始二进制可从已有 VFS/工作区缓存按需读取；physics 的组件字节不等于 Mesh/Renderer 等全部原生输入。

旧 `EiemPackageWriter.WriteRenderer` 在输出装配前按 Mesh 去重，会省略共享同一 Mesh 的后续 Renderer 使用上下文。本轮已修改：几何和作者 INI 资源动作仍去重，但先导出每个使用者的材质；新增 `source/manifest.json` 保存全部 Renderer 使用、精确 Shader/资源引用和原生状态来源。配套 `source/serialized/` 与 `source/streams/` 保存本次 PFB 依赖闭包的完整原始字节，未知字段不通过 JSON 重建。这些来源文件只服务解包编辑与工作区验证，不发布到 Mod。

Blender 到 C++ 的输入是连续内存缓冲区加描述信息，不要求先写出新中间文件。输入 ABI 有版本、类型/步长、长度和所有权契约，但这是内存接口，不能把它误认为解包磁盘格式也必须重做。

最终游戏输入使用游戏兼容的原生序列化格式。当前发布采用 INI 加独立 Mesh/Material/Texture 增量文件，由 INI 统一描述资源身份、部件展开、引用和控制；插件在当前资源加载输入上重建合法原生序列化数据。旧解包格式服务编辑，新输出服务原生加载，职责不同；保留前者不代表游戏继续使用旧运行时 Mesh setter。必要时只为确实表达不了的新作者数据升级相应字段/载荷，不能因执行路线改变就要求所有已有 .blend 重新制作。

原生字段可正确回读，不等于修改后的功能组合能沿用原存储。当前身体源 Mesh 没有形变通道，作者 Mesh 新增两个；最终写入器必须将已支持的 packed normal/tangent frame 展开成 Float32 normal3/tangent4，供原生形变/CPU 蒙皮路线处理。无形变 Mesh 保留原支持布局。转换在反序列化前完成，更新描述符与数据的一致关系，保留各 Mesh 的骨骼 palette、形变及材质/贴图引用。用户不需要手动选择 stride 或更换作者文件格式，具体规则和支持边界见 [顶点数据契约](vertex-data-contract.md)。

离线打包实验和增量导出已完成，静态原生输入修复构建已部署；部署与游戏验收的区别见 [DLL 接入边界](dll-resource-input-validation.md)。来源格式及验证边界见 [解包来源基线](exporter-source-baseline.md)。

## 用户操作和工具职责

Blender 继续作为主要编辑界面。当前导出按钮直接采集编辑快照，读取所保留的实际原生来源 schema，生成格式 2 的 INI 与独立资源。C++ 解析器与游戏写入器共享来源格式代码，几何编码目前由 Python 完成；不先写旧编辑 Mesh 中间文件。

## 内嵌原生库的执行边界

Python 负责 Blender 数据访问、选择和界面；连续 NumPy/内存缓冲区通过明确类型、长度、步长和所有权的接口传给原生库。优先使用 `foreach_get` 批量读取，不逐顶点跨语言调用，不把大数组转为 JSON 或先组装大量 Python tuple/list。首次实现允许为一致快照复制一次；只有生命周期与修改契约明确时才减少这次复制，不能为了零拷贝持有失效数据。

C++ 负责面角属性对应的顶点展开、材质分部、坐标/索引转换、权重与形态数据重映射、内容校验/哈希、资源序列化和最终写出。维持源顶点到输出顶点的显式映射；优化不能改变旧导出精度、UV 接缝、权重或形态语义。新单材质部件结构不继续执行旧多 submesh 强制合并。

仅 Blender 主线程访问 bpy。原生后台任务消费稳定快照，不访问 Blender 对象或其私有 DNA 内存；异步队列持有数据到任务结束，Python 释放 GIL 的接口方式需要实现验证。内嵌本身不会让同步计算自动变为异步，也不消除 Blender 的几何计算/数据读取成本。

同一个原生核心可由小型命令行验证程序调用，避免另做一份序列化实现。该库属于作者工具端，游戏 DLL 继续负责资源加载及运行时控制，不在游戏帧循环执行 Mod 构建。

目前源码仍在 `export_corner_map` 的字典循环、坐标/UV/三角形列表处理、权重/形态导出和缓存内容摘要中执行大量 Python 循环，存在移交原生核心的具体计算项。已使用 NumPy 的部分不因此重复实现；最终速度以数据采集、转换、纹理及写出分段计时为准，不能从“使用 C++”直接推出固定加速倍数。

| 环节 | 输入 | 输出与责任 |
|---|---|---|
| AnimeStudio 解包 | 当前游戏资源与索引 | 可编辑 Mesh/Material/Texture、源逻辑身份、骨骼槽绑定、实际 Renderer 装配上下文、原始序列化对象/schema/依赖资料 |
| Blender 编辑与准备 | 解包作者包和用户编辑 | 版本化作者快照：数组、对象身份、材质属性与贴图、目标源 Mesh、LOD、部件显隐及形态控制声明 |
| 独立打包工具 | 作者快照与兼容的游戏格式资料 | 几何分部、校验、原生资源序列化、依赖建立、纹理处理、统一装配规则、构建清单与最终 Mod 包 |
| 游戏插件 | 完整 Mod 包与游戏正在加载的资源 | 按当前源资源身份应用同一装配规则，将资源交给游戏创建/初始化；后续控制显隐、形态值及已验证的刷新协议 |

独立打包工具可以先做命令行程序，复用 AnimeStudio 的读取代码，并将新写出器放进可共享的纯格式库；暂不需要建立另一个 GUI 或新仓库。不得重复维护两套游戏格式序列化实现。

## 解包侧需要增加的内容

1. 以真正的资源入口 `AssetBundle.m_Container[].Value.asset` 与组件 PPtr 读取装配，不继续用同名根节点作为准确性依据。此读取办法已在 46 个候选 PFB 的离线检查中验证，本轮已接入正式导出入口并在目标 PFB 重新导出中验证。
2. 每份 Mesh 保留逻辑资源容器、子资产身份、类型，以及本次索引解析出的 CAB/PathID。逻辑身份用于规则，物理对象 ID 用于本次版本精确解析；不可把本次 CAB/PathID 当成跨版本固定值。
3. 单独保存 Renderer 使用上下文：Mesh、Material、bones/rootBone/skinningRoot、LOD 和相关控制关系。一个 Mesh 可以有多份使用上下文，不重复导出相同几何，也不把首次遇到的 Material 当成唯一用法。
4. 为写回提供原始对象字节、对象表、类型/schema、external 依赖及所需流数据。可由工作区当前源 bundle 按需提供，不要求每个作者包复制全部游戏依赖。未知未改组件保留原字节；描述性 JSON 不替代原二进制。
5. 反向消费者表服务预检与覆盖核验，包括 UI、NPC、过场等。生产使用源 Mesh 规则匹配当前加载记录，不以本轮 46 个 PFB 制作永久白名单。

这是增加身份、装配和写回所需的保真信息，普通 Mesh 编辑数据不必因而全部改为游戏内部格式。

## Blender 准备的数据

作者快照需要包含选中对象的几何/拓扑、按顶点或面角区分的法线/UV/颜色/切线、权重和 bindpose、材质分组、形态通道及对象变换约定。顶点组/形态数据必须与最终顶点映射一致，不能只给顶点坐标与三角形。

每个作者对象保留独立稳定部件 ID、源 Mesh 身份与各自的基础 Material 来源及属性修改。一个对象可以有多个材质面组，独立工具按这些分组生成单材质 Mesh/Renderer；不要求用户手动把所有对象按材质拆开。多个对象引用同一源 Mesh 时，保留它们各自的部件和控制语义，不再为了旧执行器强制合并成多 submesh 的最终 Mesh。

Blender 特有的数据读取、编辑状态刷新和所需几何计算仍在 Blender 内进行。后台工具只消费完成且一致的快照，不通过 MCP 逐顶点传输，不直接解析 `.blend`，不在工作线程调用 `bpy`。

现有 EFFMESH v6 可作为迁移期作者几何载荷候选：纯 `eiem_format.py` 不依赖 bpy，已有权重、bindpose、形态及来源信息。仍需增加部件/材质/装配规则清单并审查数据完整性；EFFMESH 自身不是游戏原生 Mesh 文件，也不能宣称旧 Mod 包可直接用于新资源路线。

按键与形态变量声明放在同一份 mod.ini，映射到部件 ID 与形态通道。多个按键共同写状态，部件最终条件读取状态。单材质结构的显隐不沿用修改运行中索引的旧逻辑。物理和新增骨架继续留在后续阶段。

## 构建和加载的分工

独立工具负责离线昂贵处理与校验。最终 Mod 包应包含合法原生资源载荷，以及“源 Mesh 到部件列表”的统一装配规则。当前版本可批量物化 PFB 补丁作为写出/覆盖验证产物，但发布架构不能依赖永久保存全部旧 PFB。

加载当前游戏 PFB 时仍需应用相应结构变换。离线构建与加载变换是同一资源路线的两个阶段，不是两套替换路径。纹理转换、几何分部、作者数据遍历等不应放入帧循环；结构变换时机与结果缓存需要基于真实加载入口验证。

冲刺的消融实例仍由游戏从登记后的 Mod 基础材质创建。通用残影模板的 Mesh 初始为空，不给它写死角色 Mesh；新增部分进入原生 Renderer 登记和捕获仍是必要实机验收项。

构建应在独立输出目录完成，所有资源与引用校验通过后发布完整代际，让 F10 读取完整输入。构建成功不证明游戏原生资源/实例重建协议已实现，F10 的原生入口仍待验证。

## 性能边界

现有导出器已使用 NumPy、批量 `foreach_get` 与会话增量缓存。当前连接的 Blender 5.0.1 工程有 80 个带源 Renderer 元数据的 Mesh 对象，最大样本有 108161 个顶点；这些是场景统计，不是全选导出或耗时测试。

把最终打包移到独立进程可以减少 Blender 阻塞，并允许几何编排、压缩、纹理处理与序列化使用更合适的实现。它不能消除 Blender 读取和计算编辑结果的成本；若旧的角点展开、合并、编码仍全部执行一次，再交给工具重做，总工作反而可能增加。

后续测量应分别记录 Blender 快照采集、几何转换、纹理编码、原生写出和 PFB 变换耗时。按作者资源增量复用未改输出，不每次扫描完整游戏；缓存键包含作者内容/声明、源格式兼容信息及打包器版本。这是构建缓存，不用作游戏内 Mesh 资源指纹匹配。

## 实施顺序

先利用现有作者载荷实现一个 Mesh 两个材质部分的独立写出/校验样本，证明原生资源写出和装配变换。通过后再改 Blender 的快照与启动入口，把适合后台完成的角点展开、分部、编码工作移出。保持用户操作集中在 Blender，避免先重写整套 UI 后才发现原生写出不可用。

本方案尚不能承诺完整跨版本兼容、最终构建速度或 F10 稳定性；这些分别由序列化格式、计时和原生刷新验收决定。
