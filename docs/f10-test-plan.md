## 先观察一次游戏自然重建

用户建议通过队伍切换、角色展示和地图切换观察自然生命周期。它适合验证资源缓存、模型实例池和 Renderer/helper 重登记的真实调用次序，先于下面 F10 A/B。不修改作者文件，不按 F10。

当前 `full-reload-observation.enabled` 已存在，运行 DLL 包含 helper 初始化/重查/释放、材质登记/释放、模型 set/load/remove 及 Bundle 读取/卸载的只读记录。GFX 不需要启用。自然切换已经在 v35c 会话 pid 26220 记录；v2 探针补齐代理退出及协程创建边界，待下一次游戏会话验证。

用户在一次新进程里按顺序操作：

1. 进入世界，使用 LZY，走动、平 A 一次，作为基线。
2. 切到另一角色，再切回 LZY，两次操作各停留约 5 秒。这一操作可能只是显示/激活切换，若没有重建是有效结果。若希望检查移除/加入队伍，应另外明确执行这一操作，不把换操控角色当成移除实例。
3. 打开角色展示页，切到另一角色再切回 LZY，返回世界，各停留约 5 秒。
4. 传送到另一个地图/区域，载入完成后再返回，检查 LZY，最后正常退出。

日志分析目标：

- 哪些操作只改变可见性，哪些复用闲置模型，哪些重建模型根或 Renderer。
- 新旧 Renderer 使用的 Mesh 对象是否复用，骨骼槽/rootBone 是否仍属于对应实例。
- helper/material/capture 的初始化和释放顺序，是否自然调用 ReFindRenderersInChildren。
- 目标 Bundle/Prefab 是否发生实际 load/unload，不能把新的角色实例等同于再次解码资源。

现有装配记录有 Renderer/Mesh/bone/rootBone 指针与计数，尚未完整记录所有 Material/Texture/Animator 对象连续身份；不能仅靠这些指针宣称完整缓存复用或 Animator 保留。事件每边界 128 次、资源日志 256 次有采样上限，本轮若达到上限或某路径没有被覆盖，“未出现日志”不证明“未执行”。不足的证据先按实际缺口补齐，不能让用户重复同一组操作并把缺失当成功。

自然切换使用的是当前游戏资源版本，不会主动加载磁盘编辑后的 Mod。调查要产出可以复用的注销/创建/登记次序；F10 还必须准备新资源并让新 Renderer 取得它们。UI/world 可使用不同 Prefab，比较时保留各自逻辑来源，不将跨 Prefab 对象差异误判为缓存失效。

## 第一轮：一个游戏进程内完成贴图 A → B → A

### 我负责的准备

1. 核对实际加载版本、Mod 输入与离线候选版本，保存测试前的日志位置和文件摘要。
2. 导出 B 后确认 `textures/body.tex` 的像素确实变化；Mesh、材质、INI 在这次纯像素修改中保持。如果其他文件变化，记录真实原因，不把测试误当成只改贴图。
3. 游戏结束后定位这次 F10 的完整日志：收到按键、所选版本、原生加载、实例化路由、动画恢复、迁移/提交或失败/回滚。日志由我分析，不要求用户自己阅读。

### 用户操作

1. 先启动游戏进入 LZY 的世界场景，确认当前模型、走动和平 A 正常。这是贴图 A。**先启动，再改图片**；提前改图会使冷启动直接显示 B，失去 F10 前后对照。
2. 备份 `G:\zmd\lzy\body.png` 到 Mod 输出目录之外。在原图片上加一块容易看到的绿色或紫色标记，保留透明度，第一轮保持尺寸和文件路径不变。这是贴图 B。
3. Blender 选中引用这张图片的身体 Mesh，用“导出所选 Mod → 仅贴图”。输出父目录为 `D:\Hypergryph Launcher\games\Endfield Game\plugin\mods`，Mod 名 `LZY`。等待导出及自动编译完成，不手动操作 EXE、不编辑 INI。
4. 回到同一游戏进程、同一场景，按一次 F10。观察身体标记是否出现、多久出现；随后走动、平 A、检查身体残影和已验收的部件按键。头饰 toushi 的原版贴图也应保持。不要在请求后立即退出。
5. 导出完成后若 F10 按下约 10 秒仍无变化，记录“未变化”，无需盲等一分钟或连续按键。这里 10 秒是本轮诊断观察窗口，不是声称程序有 10 秒超时。我检查后台状态后决定是否仍需等待。
6. B 显示且动画等正常，才恢复 PNG 备份，再仅导出贴图并按一次 F10，检查 A 是否恢复。若第一步失败或模型异常，停止后续修改，保留这次日志。
7. 同一轮通过后，打开角色展示页面，切到另一角色再切回 LZY，返回世界，检查后来实例化的模型也使用当前版本。最后正常退出。

外部编辑图片时，如果 Blender 的图片带有尚未保存的绘画修改，导出器会优先采用该绘画缓冲；应先明确保存或重新加载图片，避免把旧缓冲当成新磁盘 PNG。

### 这轮的通过判据

- 当前身体 A → B 可见，恢复导出后 B → A 可见。
- 不能只有 PREPARED/LOADED：v35c 路径必须出现实际 ROUTE、CONSUMERS、MIGRATED、COMMIT，且视觉变化一致。
- 走动、平 A 和残影正常，没有 T pose、撕裂或模型丢失；按键与形态控制仍可用。
- 原版头饰贴图保持；后来创建的世界/UI 实例使用当前版本。
- 不要求该路线 root/Animator 对象身份保持：v35c 会重建模型。如果后续改用贴图局部更新，则以 root/Animator/Mesh 身份不变作为额外判据。

## 失败怎么分流

| 实际证据 | 下一步 |
|---|---|
| 没收到 F10 | 修按键输入或焦点，不碰资源加载 |
| TEX 像素没变或选了旧版本 | 修 Blender 图片来源/发布与请求版本；不重建角色 |
| 收到请求但候选资源加载失败 | 定位第一个失败资源、共享依赖及缓存身份；旧模型应保留 |
| 候选加载完成，实际实例化没有 ROUTE | 修实际工厂入口或代理缓存路径；不得把空提交当成功 |
| 已路由但材质仍引用旧 Texture | 按真实对象引用处理材质副本、模板、特效消费者；必要时切到贴图局部更新 |
| 迁移或回滚导致 T pose | owner 重建链未成立；优先实施贴图局部更新，保留角色实例。Mesh 重建另行验证 |
| 世界成功，展示或以后实例失败 | 修缓存 Prefab/实例池及未来创建的版本选择，不让用户重启冒充热重载成功 |

若改用新建 Texture 的局部路径：上传 TEX 内已生成的像素和 mip，按旧 Texture 对象身份更新使用它的材质；不能通过同名贴图或统一 renderer mask 覆盖所有对象。也不调用 RemoveMainPart/LoadMainModelSync。当前新增贴图不可读，直接原地 LoadRawTextureData 路线不能未经处理就启用。

## 最后验收性能与重复加载

将以下时间分开测量，不再把导出准备、离线编译和游戏提交混为一个数字：

1. Blender 从点击导出到完成。
2. 自动编译器准备候选。
3. F10 收到请求到提交。
4. 游戏主线程最大单帧提交时间；异步工作耗时和卡顿分别报告。

现有仅贴图完整准备曾测到约 29 秒，原生候选加载曾测到约 1.16 秒。它们属于不同阶段，不能保证新一轮同样耗时，也不能宣称已经毫秒级。

各资源单项通过后，做一次代表性重复测试：不同版本连续替换、未修改时再按 F10、展示/世界切换、地图重新进入。检查本插件持有的 Bundle/Texture/Mesh/GC 引用不持续增长；进程总内存只能作为辅助，不能单凭涨跌判断泄漏。没有全局 UnloadAllAssets 或强制销毁游戏共享资源。

## 本次给用户的最小反馈格式
