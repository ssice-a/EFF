# Mesh 目标运行时路线：2026-10-28 命中验证

当前已进入下方“真实资源与交付验收”阶段。前半部分保留命中测试的历史结果；它们不是新资源创建／完整替换的性能数据。

本轮按用户确认重新验证“游戏加载对象后，按 Mesh 身份匹配”的路线。旧动态装配文档的取消状态仅描述此前决定。本轮没有切换生产替换架构，也没有预编译任何消费者 PFB。

## 本次实现

独立构建开关 `EIEM_MESH_TARGET_PROBE`，脚本为 `tools/diagnostics/build_mesh_target_probe.cmd`。测试 DLL 直接读取已安装 Mod 的 `mod.ini`，检查声明的 Mesh/Material 文件存在，读取目标路径、子资源名称、LOD、Part 数量和 skip 规则。它不读取资源载荷、`compiled.bin`、PFB 来源清单或游戏索引文件，也不运行编译器。

普通构建保持现有生产后端；命中测试构建关闭其启动准备、后台编译包轮询和 F9/F10 资源更新。测试构建不会替换模型，因此显示原模型是预期结果。不能将测试构建作为发布 DLL。生产二进制检查器会拒绝包含 `[MESH-TARGET-` 标记的产物。

1. 只向游戏当前资源目录查询 Mod 声明的目标，获得当前 Bundle key 和子资源 hash。游戏 Mesh 字节、物理存放位置变化不参与失效判断。
2. 实际收到一个原始 GameObject 资源时，向原生目录查询该请求所属 Bundle 的完整依赖；用目标 Bundle 集合筛选，包含 Bundle 自身。只使用正向依赖，不反查消费者，不枚举游戏 PFB。
3. 未命中 Bundle 筛选的资源不检查层级。候选只调用原生 `GetComponentsInChildren` 检查已经加载的局部 Renderer；这仍有首次遍历成本，必须实测。
4. Mesh 名称仅作二次筛选。最终匹配通过目标确切 Bundle 的原生 Mesh 对象与 Renderer 的 Mesh 对象相等来确认；FBX 子资源使用当前目录返回的 hash。只查询已经加载的目标 Bundle，不另外请求尚未加载的角色资源。
5. 原始 `AssetProxy.Get`、资源 handle Get 和 Prefab proxy preload 观察资源交付；六种同步/异步实例化边界核对是否已有来源匹配。新剧情 PFB 在它实际加载时执行同一逻辑，无需离线列出路径。
6. 加载线程只登记目录/池位置或退休事件，不进入 Unity 加载 API、不等待主线程匹配锁。目录解析和实际 Mesh 查询在主线程执行。源对象缓存使用弱引用、InstanceID 和固定条数上限；Bundle 退休会清除目标 Mesh 身份。

## 测量与判定

`plugin/eff_log.txt` 中记录：

- `MESH-TARGET-DIRECTORY`：INI 读取时间与目标数量。
- `MESH-TARGET-MANIFEST`：目标身份绑定时间、缺失目标；该成本单独记录，不隐藏在后续缓存命中中。
- `MESH-TARGET-HIT`：Mod、规则、LOD、实际 PFB 路径、Renderer/原生 Mesh 身份及交付边界。
- `MESH-TARGET-DELIVERY`：来源在原生实例化之前已命中。异步记录证明提交边界，不证明异步完成/实际替换。
- `MESH-TARGET-CONSUMER`：利用游戏已有 Renderer 列表，观察材质控制器/Helper 初始化时是否仍有未经早期来源匹配的目标 Mesh。此计数按 Mesh 身份核对；同一 Mesh 曾在别的 Prefab 命中过，不能据此证明每个实例的来源覆盖。
- `MESH-TARGET-STATS`：筛选查询次数、候选和真正命中的 PFB 数、层级遍历次数/最大耗时、Mesh 查询时间、初始化审计成本及缓存条数。`unobservedCloneCalls` 包含非 GameObject 克隆，不能直接解读为目标模型漏拦截数。

Bundle 依赖是保守筛选。如果游戏把许多资源打进同一 Bundle，候选可能较多；须检查 `candidates` 与 `matchedPrefabs` 的差距和最大遍历时间，不能凭算法微测量声称游戏内没有卡顿。资料不足时记录 GAP 并保持可重试，不把它保存成永久未命中。

本机声明读取检查：8 个 Mod、194 条目标（含全部声明 LOD/FBX 子资源），一次读取约 19 ms。20 万条无关依赖筛选约 10 ms、层级检查为零；这只是独立测试程序的算法测量，不是游戏首次加载或完整替换耗时。

回归覆盖负筛选、同名不同对象、从未列出的剧情 PFB、六种原生工厂调用、重复交付去重、对象 ID/弱引用退休、原生主资产/FBX 精确查询、未加载资源不发起请求、依赖证据迟到后重试、加载线程不等待主线程匹配锁。游戏内世界/NPC/UI/后来加载的剧情仍须实测。

## 真实资源与交付验收：第一段实现

`EIEM_MESH_NATIVE_ACCEPTANCE` 构建复用上面的精确命中，仅对已安装 chen 包的身体单 Part 启用真实替换。它不是完整生产后端，其他角色和 chen 裙子仍为原模型，按键／形态控制、新骨骼、物理、特效和 F10 均未迁移。本段没有重新导出 Mod，没有预编译消费者 PFB。

新增 `eiem_runtime_resource_payload.h` 直接读取 EFFRES2 的已命名字段，核验索引、顶点流、权重、骨骼和稀疏形态。顶点／像素借用已校验资源字节，不再复制整份缓冲。矩阵特别处理：序列化 bindpose 字段为行顺序，Unity 托管 Matrix4x4 为列顺序，创建时转置并读回核验。作者资源的旧游戏 schema hash 不作为当前游戏的拒绝条件。

现有 chen 的 20 网格、9 个独立贴图文件共 212,817,146 字节在独立检查器通过，覆盖 61,031 顶点、2 个形态、19 个压缩帧网格和 39 个带标记的属性。包括破坏索引、描述符、权重和贴图尺寸后的拒绝检查，耗时约 0.55 秒；这是有系统文件缓存的独立工具测量，不是冷存储／游戏内加载时间。身体自身只读取 7,467,998 字节，单独检查约 19 ms，同样不是游戏内完整替换耗时。

原生创建通过元数据绑定的 Unity Mesh／Texture2D／Material 接口，不写私有原生布局。完整骨架路径在每个隔离模板内解析，低 LOD 身体也使用同一作者网格和贴图。材质 donor 通过当前目录的确切逻辑路径从已加载 Bundle 解析，不按全局名称借用。贴图上传后释放其原生 CPU 像素副本。

序列化的 dimension 高位不是公共 Mesh API 的分量数；不能把 `0x24` 直接当成 36 个分量传入，否则可能越界读取。当前身体的 UV 使用实际四个 Float32 分量创建并保留值，游戏特殊 UV 标志在该公共表示下的 Shader 效果尚待实机验收。19 个压缩法线／切线网格暂不进入原生创建，明确拒绝，不能把一个压缩字当普通法线。解码器能识别它们不等于已证明原生创建支持。

交付先创建一个未激活的隔离模板，改其身体 Renderer 的网格、材质、完整骨骼槽位和包围盒，再交给六种原生实例化入口；原始游戏资源不修改。Helper／Cloth 的 Awake、OnEnable 和初始化列表受审计，若模板构建期间提前初始化则拒绝发布。模板按实际加载来源保存一份，网格／材质／贴图跨模板共享；来源退休后回收模板。这段验收会在进程内保留一份身体资源，尚未验证生产级 owner 租约回收。

磁盘读取和校验在首次实际命中后交给纯磁盘工作线程。**此验收段在首次实例化处同步等待自己的工作线程并测量等待时间；尚未实现生产级异步交付门，不能宣称首帧不卡顿或已消除完整替换的准备时间。**它不等待游戏 ResourceManager 队列，也不预读全部 Mod。

实机需要分别确认：`MESH-NATIVE-API/READY`（真实接口）、`RESOURCES`（读取／创建／上传及整进程内存样本）、`ASSEMBLED`（未激活模板与骨骼）、`DELIVERY`（实际提交作者模板）、`CONSUMER`（游戏初始化时仍使用作者网格／材质）。这些证据与画面均通过后，才能继续把 0/N Part、压缩帧转换、新骨骼／物理／特效及 F10 接入该后端。独立宿主 DLL 加载测试不初始化 Unity，不能代替这些实机验收。
