# 首次资源准备耗时探针（2026-11-17）

上一轮游戏进程 42184 正常退出。日志中首次命中的依赖组准备在主线程耗时
66–473 ms；启动扫描为 80.562 ms，且未预读资源负载。此前内存采样开始于
游戏退出后，不能据此判断游戏运行中的内存稳定性。

本次仅补测量，不改变资源发现、按需读取、编解码、发布、动画或热重载策略。
既不预载全部 Mod，也不扫描游戏索引。

## 待验证假设

1. 实际读取或解压占主导：慢组的 `readMs` 或 `decodeMs` 随 `wallMs` 增长，
   并有相应读取字节、解压次数。否则排除这一主因。
2. 元数据、材质或消费者反复解析占主导：读盘时间较低，但 `layoutCalls`、
   `metadataMs`、`materialsMs`、`consumerMs` 较高。否则应转查其他阶段。
3. 锁竞争或代际提交占主导：`sharedWaitMs`、`scopeWaitMs` 或 `isolateMs`
   接近总耗时。若这些时间很小，则不能把慢加载归因于锁或发布。

## 测量边界

使用已有 `build.bat load-perf`，产物单独位于
`bin/resource-directory-entry-format3-load-perf/`。只有 `EIEM_LOAD_PERF`
构建启用计数、QPC 和 `[DEBUG-loadperf]` 日志；生产构建为无操作接口。

既有五秒统计补充以下阶段：

| 阶段 | 边界 |
| --- | --- |
| demand-shared-wait / demand-scope-wait | 获取共享准备锁、Mod 代际准备锁 |
| demand-discovery | 当前游戏请求的依赖与逻辑目标发现 |
| demand-open | 未打开的请求输入：VFS 查询、文件打开、原生目录读取 |
| native-read | 实际文件锁、定位与 ReadFile；记录成功读取字节 |
| native-decode | 准备期间缓存未命中的数据块解密、解压和缓存整理 |
| native-stream-decode | 原生输入交给游戏后，流式视图按需解压 |
| native-directory / native-metadata | Reader 目录构造、序列化对象元数据解析 |
| author-snapshot | 首次命中的作者文件不可变快照；记录快照字节 |
| demand-compose / demand-carrier | 组合作者声明、准备 Mesh 载体 |
| demand-material-uses / demand-materials | 收集当前消费者材质用途、准备共享材质 |
| demand-consumer / demand-edit-commit | 修改消费者、提交成员重写 |
| demand-view / demand-roots | 构建虚拟输入视图、代际根输入 |
| demand-isolate / demand-publish | 隔离原生成员身份并提交图、发布已准备输入 |

每个实际完成的冷组、失败组及超过 10 ms 的缓存/不相关请求另有一条
`demandBreakdown=1`，携带原生请求身份、结果和各阶段时间。数据存于当前线程
的局部样本，嵌套请求计入父请求，其他线程不计入该请求。请求结束与异常展开
均恢复前一个样本，不影响资源生命周期。没有逐对象或逐字段日志。

所有阶段均为包含子阶段的墙钟时间，不能相加。例如元数据解析可能包含读盘和
解压。`streamDecodeMs` 只包含该组尚在准备时发生的流式解码；稍后游戏读取的
流式解压出现在五秒阶段统计中。进程/GPU 内存仍是整个进程/设备的指标。

分析器保留逐组样本到 `demandBreakdowns`，不将组样本归入之前已经输出的五秒
窗口。日志、安装回执、生产回滚副本和独立内存采样置于
`diagnostics/cold-load-probe-20261117/`。

### 已确认的问题

资源发现回退范围过宽。`Current()` 将公共 manifest 无精确子资产记录的目标
放进 `unresolved`；`SharedGetOrCreate()` 等真实请求入口只要看见这一列表
非空，就允许 `PrepareDependencyGroup()` 检查该请求及其依赖中的原生容器。
其中有本可通过已知路径路由约束范围的 `.asset` 目标，也有本轮没有公共查找
记录的武器 `.fbx` 子资产。按代际缓存阴性结果避免了相同输入无限重查，但
不能阻止大量新的无关请求进入这段解析。

- 最慢不相关请求：346.928 ms，其中发现 342.956 ms，读盘 138.276 ms、
  元数据 249.686 ms、解压 130.927 ms。后三项相互包含，不应求和。
- 进入场景时 `demand-prepare changed=0` 累计计时 12,571.723 ms；
  `demand-discovery` 为 11,868.494 ms。此为主线程函数墙钟累计，不能再与
  父阶段或子阶段相加，也不是插件启动声明解析的耗时。
- 实际完成的替换组约 5–303 ms。302.869 ms 的组中，发现 53.272 ms、
  Mesh 载体 75.281 ms、材质用途收集 70.492 ms、消费者 34.336 ms、
  代际隔离提交 24.034 ms；这是另一类需要继续缩减局部序列化工作的冷命中。
- 前三个冷命中组的作者文件不可变快照累计分别约 107.004、95.938、115.876 ms，
  已包含在载体/材质等父阶段中；后续命中组快照时间为零。优化时应继续保留旧
  代读流的隔离保证，检查同文件租约的复用，不能直接删除快照保护。
- 锁等待接近零，不支持“主要是锁竞争”的假设。
- 打开展示页期间还有一次 `effect-load-step` 136.864 ms，包含原生加载调用。
  需要与数据发现和常态维护分别评估，不能全部认定为 EFF 自身 CPU 求值。

下一步优先缩小目标发现范围：对已经获得游戏路径路由的目标只检查相应请求；
缺少公共路由的子资产从当前请求的 Renderer/Mesh 原生引用追踪到精确载体，
避免把整组依赖都作为候选容器。必须以嵌套 PFB、跨 CAB Mesh、全 LOD、多个
Mod、重定向/恢复和 F10 新代际作为回归条件，不能简单关闭未解析目标的回退，
否则本轮确实依靠回退找到的武器会失效。后续已实现来源范围修正，源码回归与
部署状态见[修正记录](cold-load-discovery-fix-20261117.md)；本页保留修正前的测量值。
