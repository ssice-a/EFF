# 不同角色使用同一作者模型：发紫与恢复原皮调查

2026-10-19 外部用户反馈：同一模型为不同角色制作 Mod，贴图有时发紫；两角色同时在场时其中一个恢复原皮。初次调查时没有两份包、DLL 摘要或异常会话日志；本机未复现游戏画面。同日已收到一份 eff_log，新增证据见下一节；仍缺出问题的两份完整包与对应 Player.log。

作者补充：两份 Mod 的材质应当不同，另一份可能保留 Si 原材质。因此不能把“相同作者模型”理解为“相同原生材质”，也不能仅测共享材质模板后宣布资源路径已经排除。

这是独立于新增特效支持的现有资源兼容调查。没有为此替换游戏 DLL、改动现有 Mod 或发布修复。

确认的配置问题是 **重复 Mod ID**；材质不同并不能避免此类身份冲突。它拒绝整套候选，不是随机把两份材质合并。目录改名不改变 INI/compiled.bin 中已编译的 Mod 身份；不同角色版本应当用独立身份重新完整导出，不能只手改 id 后保留原 compiled.bin。

仍待验证的运行时问题按预测区分：

1. **池实例或源 Prefab 路由漏过**：路径未变、无新提交，同一路径由 14 个作者网格变为 0；需要实例来源、原生工厂/池与当前候选对象身份。
2. **候选资源生命周期**：候选/Shader/Mesh 在首次有效后退出，后来仍复用旧候选或失效路由；需要资源退出、原生存活性和 Player.log 的 Shader/Bundle 信息。
3. **实际两包编译资源组合冲突**：需把该两包直接送进现有共享输入回归；目前本机 fixture 通过不排除外部包的问题。

日志中的候选校验只证明当时通过，生产日志没有后续 Shader 状态/卸载事件，不能把“没有 Shader 错误行”解释为 Shader 一直正常，也不能据此确认发紫根因。当前尚无用户画面的自动复现，不进行猜测性 DLL 修复。机器可读时间线保存在本机 `bin/multi-mod-user-log-analysis-20261019.json`；没有复制/修改原日志或外部 Mod。

## 已确认的边界

- 新增 Material/Texture 的 PathID 包含 CAB、Mod ID、资源 section；新增 Mesh 还包含精确目标路径与资产名。runtime part 标记包含 Mod/Part/目标身份和作者 Mesh 摘要。作者物体、贴图同名或像素相同不直接等于原生 ID 冲突。
- 重复 Mod ID 会在候选集合组成时拒绝整个候选。启动拒绝可能表现为未启用替换；F10 拒绝时保留已提交的旧集合。不能从“原皮”反推只有一个对象被覆盖。
- 当前不会以作者 Mesh 名或贴图名选择人物实例。资源路由使用具体来源，模型候选路由核对原对象与实例 ID；这不证明所有未知游戏池/加载场景已经正确。
- Unity 整片洋红通常提示 Shader 缺失、不支持或加载失败；缺贴图不必产生相同表现。必须查看材质/Shader/资源加载证据，不能直接归因到 UV 或贴图名称。

## 当前验证

本机安装六份不同 Mod，共 320 个来源，其中 50 个来源被多份 Mod 共同修改。只读清单与真实集合准备/输入摘要检查通过，未发现重复 Mod ID 或跨 Mod 相同作者载荷的摘要，因此本机当前包不是反馈所描述的确切组合。

`compiled_mod_set_smoke` 新增成对作者资源测试，在真实共享输入合并入口分别验证：同原材质模板，以及不同 Material/Shader/原 Texture 模板；作者命名/像素仍保持相同，分别绑定两个角色 Renderer。再验证一方使用作者材质、另一方保留原生材质。改变贡献顺序，核对独立 Material/Texture ID、准确 Shader/Texture/Renderer 引用、流式数据范围及原生材质保持。startup/isolated 两类输入均通过。它验证离线组成边界，不代替反馈场景的游戏复现。

证据为 `bin/multi-mod-isolation-tests-20261019.log`、`bin/multi-mod-installed-set-20261019.log`；采集工具 fixture 验证见 `bin/multi-mod-collector-tests-20261019.log`。可分发的工具包是 `bin/EFF-MultiMod-Diagnostic-20261019.zip`，不包含本机采集的用户日志。当前无生产修复结论。

现有共享来源、外部引用、增删对象、preload、LOD/helper 和注册合并回归继续保留。发现测试失败必须先核对 fixture 与真实调用条件，不能把测试设置错误当成生产根因。

## 外部用户双击采集

将 `tools/diagnostics/Collect-EFFMultiMod.cmd` 和同目录的 `.ps1` 放到同一文件夹。双击 `.cmd`，选择包含 `Endfield.exe` 和 `plugin` 的实际游戏目录；ZIP 默认生成在桌面。也可将两份文件复制到游戏的 `plugin`，工具自动使用父级游戏目录。

先同时启用两份 Mod，触发发紫/恢复原皮，再在重启游戏之前采集。提供角色名、Mod 文件夹名、单独安装各自是否正常，以及首次异常前是否按过 F10。

ZIP 包含：

- 当前 `eff.dll` 摘要、每份 Mod 的 ID/声明、`compiled.bin` 摘要和时间。
- 作者载荷的长度、类型及容器声明的内容摘要；**声明摘要没有重新验证全部资源字节**。
- `eff_log.txt`、`eff.ini`、Player.log/Player-prev.log（若存在），以及采集时间。
- 重复 Mod ID、缺少编译包/资源文件、异常资源路径、跨 Mod 相同载荷摘要的结构检查。

工具不联网，不修改游戏/Mod，不复制模型、贴图或完整 compiled.bin；日志和声明包含本机路径，分享前可以检查。该 ZIP 用来定位异常路径；若需重现编译组合，还需要出问题的两份完整 Mod，由反馈用户自行提供。

## 接下来如何区分原因

| 预测 | 需要的证据 |
| --- | --- |
| 复制后 Mod ID 重复 | 两份 INI、候选拒绝日志；改成正确独立导出后不再拒绝 |
| 共享输入组成缺陷 | 相同两份包在离线组合后出现错误 PPtr、对象/像素丢失，且可用固定输入复现 |
| Shader/依赖生命周期 | 原生包引用正确，但异常会话中 Shader/Bundle 加载失败或资源退出后失效 |
| 实例/池路由问题 | 模型来源正确、资源加载成功，但特定实例、进入顺序或 F10 后使用了原始对象 |
